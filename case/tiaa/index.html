Case study

Design system as a growth leverSpeed, Quality, Compliance at TIAA

Role
Principal Product Designer – DSPrincipal Product Designer – Design System
Platforms
Web (Angular & React), iOS and Android

At TIAA I led Ethos, the enterprise design system, from a set of fragmented legacy libraries to one system for web, iOS and Android, with its own architecture, tokens, governance and AI workflows.

The context

TIAA is the largest provider of retirement plans in the US non-profit sector. Its business pairs employer-sponsored retirement services (B2B) with advisory and investment experiences for individuals (B2C).

Governance and alignment

The problem

TIAA’s products had grown their own design systems: sixteen of them across the public site, the secure MyTIAA experience, the institutional platforms, UD and mobile. Some were on their third version; mobile had started with no components at all. Ethos had to bring them together into one.

The objectives

Bringing sixteen systems into one took more than a shared component library. Ethos was set up to meet six objectives, from how the system is built to how teams adopt it.

Consolidate fragmented libraries

Sixteen legacy systems across five product areas, brought together into one shared system: Ethos.

Adoption and governance in distributed teams

A contribution model and design reviews that keep distributed teams building on one system.

Scalability and maintenance

One token repository and versioned releases, so the system grows without multiplying the upkeep.

Cross-framework architecture

One system behind Angular and React on the web and native iOS and Android, from the same tokens.

Accessibility and compliance

WCAG 2.1 AA built into components and documentation, and validated with subject-matter experts.

Visual evolution and a brand refresh

Brand-scoped tokens and palettes, so a refreshed look reaches every product from a single place.

Research and audit

I started with an audit of the legacy systems across the ecosystem. It showed where the experience had fragmented, brought the stakeholders into alignment, and shaped the roadmap for one enterprise design system.

System architecture

I designed a modular architecture that brings design, code and documentation together into one scalable ecosystem.

Unified governance

Tokens, the Figma libraries, the Angular and React repositories and Storybook are connected, so they don’t drift apart.

Scalable layering

A change to a token or a component cascades predictably through everything built on it.

Maintainability

A shared language for design, product and engineering, which reduced technical debt.

Versioning

A structured versioning model, so updates reach products safely.

AI in the design system

Claude connects to Figma through figma-console-mcp, so the team can explore and reason about the design system in conversation: audit a component’s tokens, find inconsistencies, and explain what it finds.

In the developer’s editor

A VS Code plugin brings the design system into development, with the components and tokens available as developers write the code.

Foundations and tokens

Core foundations keep products visually consistent at scale: type, colour, grid, radius and spacing.

A semantic token hierarchy

Tokens are layered from global values through aliases to components. Brand-scoped layers and palettes resolve the same component token to each brand’s colour, which makes theming several brands possible.

One source of truth

A central token repository is the source of truth, with versioned workflows and an automated Style Dictionary pipeline that builds the tokens for every platform.

Component libraries

I designed modular, accessible and scalable components, with strong parity between design and engineering.

Parity with code

Figma variants are kept strictly in line with the Angular and React props.

Smart construction

Components are structured to use less library memory and to make designers faster.

Several brands, one library

Driven by tokens, so they scale across brands and palettes with no duplicated code or design.

Interaction states

Hover, focus, active and disabled behave the same way across every component.

Accessibility built in

ARIA roles, keyboard logic, contrast and touch targets are part of every component.

Data visualization

I developed a dedicated library for charts and graphs, so data-heavy interfaces stay readable.

Charting principles

Colour scales, grid spacing, typography, labelling and responsiveness, defined once for every chart.

Reusable templates

Modular bar, line and donut templates that theme dynamically.

Interaction models

Drill-downs, tooltips and legends that work the same way everywhere.

Responsive behaviour

Scaling rules for grids and type across viewports.

Patterns library

I delivered a pattern system that unifies recurring workflows, so products are built faster and more consistently. It standardizes the patterns for filtering, navigation, wizards, search and multi-step flows.

Shorter onboarding

New product teams learn one way to build each recurring flow, which shortens the learning curve.

Logic built in

Components, accessibility and interaction behaviour come baked into each pattern, so they stay consistent.

Faster to market

Teams assemble complex UI from patterns that are already validated, rather than starting from scratch.

Motion

Motion is tokenized, so it’s purposeful and accessible at scale. The tokens ship in the components and are documented in Storybook. Each curve below runs at the duration you pick.

Documentation

Documentation works in layers: foundations, interactive specifications and Figma instructions, so design and engineering stay aligned and anyone can find what they need on their own.

Accessibility

Accessibility is embedded in every layer of the system, so WCAG 2.1 AA compliance is consistent wherever it’s used.

Compliance built in

ARIA roles, focus states, keyboard navigation and contrast checks are built into the components themselves.

Annotated specs

Accessibility annotations sit directly in Figma and in Storybook, beside the specs they belong to.

Validated with experts

Patterns are validated together with TIAA’s Accessibility Center of Excellence.

Governance

A structured governance model sets ownership, reviews and version control for how the system evolves: core pods own the foundations, pod leads support the teams, and cross-pod resources run planning.

Federated contribution

Contribution is federated, through Jira workflows, engineering syncs and workshops that drive adoption. Squads bring their designs to the team for review in four steps.

  1. 1

    Submit request

    A squad submits its designs to the team for review.

  2. 2

    Review request

    The team is notified and begins the review, and lets the squad know it has started.

  3. 3

    Provide feedback

    Feedback goes into the squad’s Figma file: the use of Ethos tokens, components and patterns, consistency, and chances for new patterns.

  4. 4

    Coordinate next steps

    Usually that’s all it takes; a follow-up is set up when needed, and submitters track their request in SharePoint.

In summary

The biggest impact was turning sixteen fragmented systems into one, with the architecture, tokens and governance that let teams ship faster, with quality and compliance built in.

My role grew from designing components as a senior designer to leading the system, and setting the direction of an enterprise design system.
