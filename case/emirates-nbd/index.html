System architecture

The architecture is modular and driven by tokens. It connects the brands, the core foundations, the component libraries and the engineering resources teams build with.

Agentic design system operations

The system runs with a set of focused agents, each with one job. Some run automatically, on every pull request or on a schedule; others the team runs when the work calls for them. People review and approve everything they change.

Audit and assure

  • Token and brand agentRuns On demand

    Resolves every variable to its final value in each brand and mode, checks colour pairs for WCAG 2.2 AA contrast, and finds unaliased values and broken aliases. Run before releases and for migrations like the rebrand.

  • Component health agentRuns automatically: Weekly

    Reads Figma’s library analytics and summarises adoption, detachments and overrides by squad.

  • Code parity agentRuns automatically: Every pull request

    Reviews each change against the component in Figma, its variant properties and tokens, and comments where they differ.

Build and ship

  • Prototype agentRuns On demand

    Turns ideas into prototypes in Open Design, and builds working SwiftUI and React ones in Claude Code, on the design system’s own tokens and components.

  • Component build agentRuns On demand

    Updates components to match Figma’s variant properties 1:1, and opens a pull request.

  • Documentation agentRuns automatically: On merge

    When a change merges, drafts the updated usage notes, props and examples for Storybook and Notion, for the team to review.

Ideation and prototyping in Open Design

Product squads have started using Open Design for early ideas, an open-source design tool driven by coding agents. It reads the design system’s assets, so a prompt becomes a styled, clickable prototype in the brands’ own tokens and components, ready to test before anything is built.

Every change as a pull request

When a component changes in Figma, the build agent updates the code in Claude Code and opens the pull request from the same session. Automated checks run on it, the code parity agent reviews it against Figma, and the design system team and the platform engineers approve it. Agents update and review; only people approve and merge.

Inside the code parity agent

The agent compares a component’s definition in Figma with its code: variant properties against the code’s API, bound variables against the tokens the code uses, and the parts each one has. On every pull request it reads the component through the Figma REST API and leaves a review comment wherever the two differ. For deeper work I run Claude Code with figma-console-mcp, reading the live file, fixing the drift in code and putting the fix up as a pull request.

Figma architecture and governance

Libraries are isolated by purpose. That keeps files fast, and gives each one its own versioning, access control and reuse.

Components library

More than 200 components make up a modular library, with design and code in parity and every brand supported through tokens.

I track component usage continuously. It shows where adoption is growing, and where to invest next.

Rebuilding the Card

Usage audits showed cards were the most used component across retail experiences. They were also duplicated, with inconsistent structures.

I replaced 28 fragmented implementations with one composable architecture. It simplified governance, made cards consistent and made later improvements faster.

Tokens architecture

Tokens are layered, so brand, system and component decisions stay separate. That separation is what makes theming, several brands and consistent implementation across platforms possible.

An automated token pipeline

I automated the token lifecycle from Figma to GitHub, using MCP, Style Dictionary and custom transformation rules. It removed manual work and keeps every platform consistent.

Data visualization

An atomic, multi-brand data viz system serves financial reporting, wealth dashboards and analytics.

Financial data clarity

Key financial chart types are standardized, with room to customize, so insights stay clear and easy to read.

Built from small parts

Charts are composed from reusable blocks (axes, gridlines, legends, tooltips, series), so no squad starts from scratch.

Documentation

I wrote extensive documentation: how to choose a chart, how far each can be customized, responsive behavior, interaction specs, implementation guidance and best practices. One hub serves designers and developers, which made onboarding faster.

Motion

Motion is tokenized too. Duration, easing, sequencing and chart transitions are reusable specs, so every chart moves the same way.

A playground for charts

I used AI to build an iOS playground in SwiftUI and a React library based on Recharts. Both let us test chart customization and interactions, and agree with engineering on what was possible.

Native feasibility

A working SwiftUI app shows live chart configurations, parameter toggles and token-driven animation.

Interactive handoff

Developers and product managers adjust chart patterns (axes, legends, data density, motion) themselves, in real time.

Faster alignment

In sprint refinements we ran the native simulator to stress-test rendering, responsive scaling and state changes before the production build.
